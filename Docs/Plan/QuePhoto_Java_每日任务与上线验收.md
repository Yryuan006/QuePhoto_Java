## 3. 部署与回滚操作边界

### 3.1 两种可接受的访问方式

| 条件 | 部署方式 | 本周能做到什么 |
|---|---|---|
| 域名、所需手续、DNS、证书全部就绪 | 公网 HTTPS → Nginx → Java → 私有 MySQL | 本人通过 HTTPS 管理；未来前端还需单独接入验证 |
| 域名/手续尚未完成 | Java/Nginx 仅回环绑定；SSH 本地端口转发 | 本人安全使用服务器上的后台；不宣称 API 已公开上线 |

SSH 隧道示意，D6 需按实际服务配置验证端口：

```text
服务器：127.0.0.1:18080 → Nginx → Java 容器
本机：ssh -N -L 18080:127.0.0.1:18080 deploy@<服务器地址>
HTTP 客户端：http://127.0.0.1:18080/api/...
```

HTTP 只在本机和服务器回环/容器内网链路使用，公网段由 SSH 加密。不要把 Compose 端口写成 `0.0.0.0:18080`；使用 `127.0.0.1:18080:80` 之类的明确绑定，并从另一网络确认无法直接访问。JWT 认证仍保留，不能因为有隧道就删除后台鉴权。

### 3.2 最小发布顺序

1. 本地运行适当测试并构建，记录版本标识。
2. 备份现有生产数据库和当前部署配置（凭据单独受保护保存）。
3. 检查待执行 Flyway 迁移；首周只用向前兼容的新增变更，不进行破坏性改列/删列。
4. 拉取/载入新镜像，先启动 MySQL 并等其健康，再启动应用、Nginx。
5. 检查容器日志、迁移结果、数据库连接、最小健康接口；健康接口不暴露内部配置。
6. 重放登录、草稿、发布、公开查询、下架请求；验证图像 URL。
7. 保留上一版镜像、对应配置和验证记录，再确认本次发布完成。

生产机器只做运行环境，不必在上面学习和配置完整 IDE。优先本地构建镜像/JAR 后部署；实际构建与目标服务器 CPU 架构保持一致。

### 3.3 备份与恢复

首周运行目标：每天数据库备份，至少保留最近 7 份，另存一份到服务器外的受控位置；记录成功/失败和备份大小。后续可定时执行，不能只靠服务器同盘副本。密码不要直接出现在 shell 参数和历史中。

建议初始 RPO 24h、RTO 2h：分别表示最坏可能丢失一天新增内容、争取两小时内恢复。这是待演练验证的运行目标，不是已经具备的保证。更频繁维护时提高备份频率。

恢复演练在独立临时库中进行：恢复备份 → 核对作品/图片/标签数量及外键 → 启动隔离应用读取 → 验证图片 URL → 记录耗时。不能为演练直接覆盖生产库。

数据库备份不会备份 OSS 图片。本周不删除/覆盖既有 OSS 对象，原始图片另行保留；如果以后需要严格文件恢复能力，再配置与验证对象版本或独立备份。不要把“数据库能恢复”误写成“所有图片能恢复”。

应用故障时回滚到上一版镜像，保留数据库卷；先确认旧应用兼容当前 Schema。若迁移不兼容，停止写入并按演练记录恢复到独立库再切换，不能盲目执行向下迁移或删除持久卷。

适当的自动化：Service/MockMvc 验证 A02–A09 的核心规则，实际 MySQL 验证 A01/A06/A07 的约束和事务；A10–A15 使用真实 OSS/服务器人工演练并记录。没有必要为只读文档或 getter 写镜像式测试。
